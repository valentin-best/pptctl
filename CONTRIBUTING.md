# Contributing to pptctl

Bug reports, decks that pptctl gets wrong, design feedback and "I wish pptctl
could…" issues are very welcome, and so are pull requests that fix bugs.
Feature pull requests aren't accepted yet, while the API is still moving: open
an issue to discuss the idea instead. For a security problem, follow
[SECURITY.md](SECURITY.md) instead of opening an issue.

## Reporting a bug

The most useful report includes a `.pptx` that shows the problem. If you can't
share the deck, `pptctl info --json` and the failing command's output often
point to the part involved. Say which renderer you checked the result in
(PowerPoint, Keynote, LibreOffice, Google Slides) and its version, since many
deck problems show in one renderer only.

## Scope

pptctl is static analysis and safe surgery for decks: `lint`, `diff`,
`optimize`, `merge`, plus `info` and `extract` for inspection. It is not a deck
editor (shape-level `set`/`add`/`move` belong to editing tools such as
OfficeCLI or python-pptx). DOCX/XLSX support, a web UI, a plugin system, a
configuration file and custom rendering are out of scope for now.

## Building and testing

You need CMake 3.24 or newer, Ninja, and a C++20 compiler with `std::format`:
Apple Clang 16+, LLVM Clang 17+, GCC 13+ or MSVC 19.30+. Every dependency is
fetched by CMake; there is nothing to install from a package manager.

```bash
./scripts/build.sh                 # release: configure, build, run the tests
./scripts/build.sh debug
./scripts/build.sh asan            # AddressSanitizer + UBSan
./build/macos-release/pptctl info tests/fixtures/three_slides.pptx   # or linux-release
```

The tests are one doctest binary. To run some of them:

```bash
./build/macos-release/pptctl_tests --test-case="merge*"
./build/macos-release/pptctl_tests --list-test-cases
```

Before committing, install the hook that runs clang-format and clang-tidy on
the C++ files you stage (CI runs the same checks, as errors):

```bash
scripts/install-hooks.sh
```

## How the code is laid out

- `include/pptctl/`, `src/lib/`: the library. `Package` reads and writes the
  ZIP and its relationships without parsing XML; `Presentation` and the slide
  model parse only what a command needs. Keep command-line concerns out of it:
  it is meant to become a standalone library.
- `src/cmd/`: one file per subcommand. `src/main.cpp` only wires up the
  command line.
- `tests/`: `test_<area>.cpp` files, fixtures in `tests/fixtures/`, expected
  outputs in `tests/golden/`.

[ARCHITECTURE.md](ARCHITECTURE.md) has the design rationale. Two rules matter
for almost every change:

1. **Parse lazily.** Read parts as bytes and parse XML only when a command
   needs it; decks with a thousand slides must not be loaded whole.
2. **Write surgically.** Commands that write a deck re-serialize only the parts
   they change and copy every other part byte for byte. Their output must open
   without warnings in PowerPoint, Keynote, LibreOffice and Google Slides; say
   in the pull request which of them you checked.

## Conventions

- C++20. Print with `pptctl::print` / `println` / `eprintln`
  (`include/pptctl/print.hpp`); there is no `fmt` dependency, and `std::print`
  is avoided for GCC 13.
- `.clang-format` (Google base, 4-space indent, 100 columns) and `.clang-tidy`
  apply. Compiler warnings are strict for project code and errors in CI; fix
  them rather than silencing the flags.
- File-local helpers go in an anonymous namespace.
- EMU (914400 per inch) is the unit everywhere inside; convert only for output.
- A new subcommand gets `src/cmd/<name>.cpp`, a declaration and CLI11
  registration in `src/main.cpp`, and an entry in `CMakeLists.txt`. A new test
  file goes in the `pptctl_tests` list in `CMakeLists.txt`.

## Fixtures

Some fixtures are real PowerPoint files; most are generated by
`tests/fixtures/generate_fixtures.py`. Change the script and regenerate, never
the `.pptx` files by hand:

```bash
uv run --python 3.12 --with python-pptx==1.0.2 --with pillow==13.0.0 \
    tests/fixtures/generate_fixtures.py
```

Golden outputs are regenerated with `tests/golden/generate_golden.sh
./build/macos-release/pptctl`; check the diff before committing it.

## Pull requests

- One topic per pull request, on a branch, referencing its issue (`Closes #N`).
- Add or update tests, and the docs the change touches: README, the JSON
  schemas in `docs/`, `skills/pptctl/SKILL.md`, and an `[Unreleased]` entry in
  `CHANGELOG.md`.
- Adding or bumping a dependency means updating `THIRD_PARTY_NOTICES.md`.
- CI builds and tests on Linux (GCC, Clang), macOS and Windows and runs
  clang-tidy; it skips changes that touch only Markdown and `docs/`.
